# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Changed
- **The `[llm]` extra moved from `httpx` to `httpx2`, and floors `openai` at 3.5.0 to match.** `httpx` ended at 0.28.1; 2.x ships under the new distribution name `httpx2`, and openai 3.x declares that one and no longer declares `httpx` at all. The two bounds move together on purpose: `create_llm_client` injects an `http_client`, and it should come from the same library the SDK is built on. Keeping `httpx` declared would have installed a second, redundant HTTP stack (`httpx` + `httpcore` alongside `httpx2` + `httpcore2`) whose only consumer was our one `Client(...)` call.
- **This is not a workaround for a type check.** openai 3.5.0 accepts a plain `httpx.Client` and a full request round trip through one succeeds -- measured against a local server, not assumed. (The anthropic SDK used by `benchmark/` genuinely does reject the old class; that is a different situation, and the resemblance is what made the wrong explanation tempting.) The reason here is one stack, not a broken one.
- **No behaviour changes, and `LITELLM_TLS_VERIFY` in particular is untouched.** `httpx2.Client` takes `verify: ssl.SSLContext | str | bool = True` with identical semantics -- `True` yields `CERT_REQUIRED` with hostname checking, `False` yields `CERT_NONE` -- so the TLS default fixed above survives the move exactly. Verified end to end: the live gateway tests (`tests/test_text_calls_live.py`, `tests/test_figure_captions_live.py`) run text, structured and vision calls through the real LiteLLM gateway over an `httpx2` client with verification on.
- **Dependency refresh across the lock.** `openai` 2.53.0 -> 3.5.0, `mcp` 1.29.0 -> 2.1.1, `claude-agent-sdk` 0.2.135 -> 0.2.147, `pymupdf4llm`/`onnxruntime` 1.28.0 -> 1.29.0, plus `ruff` 0.16.5, `ty` 0.0.75, `cryptography` 50.0.1 and the usual transitive movement. `distro`, `tqdm`, `httpx-sse` and `pydantic-settings` drop out of the graph entirely -- they were openai 2.x's and mcp 1.x's, not ours.

### Fixed
- **The LLM client verified no certificate unless you told it to, and nothing said so.** `_parse_tls_verify_env` returned `False` for an unset `LITELLM_TLS_VERIFY`, and that value went straight into the HTTP client's `verify=...`, so the default install sent `LITELLM_MASTER_KEY` to `LITELLM_BASE_URL` over a channel an interposer could read. It failed silently in the worst direction: an unverified connection to an `https://` gateway succeeds exactly like a verified one, so no call, log line or result distinguished the two. Not a rare path either -- the LLM ToC fallback constructs this client automatically whenever a document's ToC scores below threshold, which 4 of 9 freshly fetched vendor datasheets do. **Unset now means verify.**
- **The opt-out is unchanged and still spelled four ways.** `LITELLM_TLS_VERIFY=false` -- also `0`, `no`, `off`, case-insensitive and surrounding whitespace tolerated -- disables verification exactly as before. Only the meaning of *absence* moved. Everything else, including the empty string, verifies: `export LITELLM_TLS_VERIFY=` in a shell profile is an accident, and it must fail towards verifying.
- **Pinned by tests, in both directions.** `tests/test_llm_client.py` asserts on the `verify=` argument that actually reaches `httpx2.Client`, not on the parse helper alone -- a correct parse that is never wired through fixes nothing -- and covers the default plus every opt-out spelling, so neither the flip nor the escape hatch can regress unnoticed.
- **`tests/test_sdk_integration.py` broke on mcp 2.x and would have gone unnoticed until someone installed the `sdk` group.** It reached the SDK-built server's handler through `server.request_handlers[types.CallToolRequest]`, a 1.x-only internal that 2.x replaced with `get_request_handler(method)`, and it read `result.isError` / `content[0].mimeType`, both renamed. `tests/test_mcp_server.py` already had the cross-major branch for our own server; the SDK's server is the same `mcp.server.lowlevel.Server` class and needed the identical one. The drivers now live in `tests/conftest.py` (`mcp_call`, `mcp_is_error`, `mcp_mime`, `mcp_list_tools`, `mcp_input_schema`) with both files importing them, so the next rename is one edit rather than two -- and cannot be fixed in one place and missed in the other, which is what just happened.

### Compatibility at a glance
- **This is a behaviour change for anyone pointing the library at a gateway whose certificate the local trust store does not accept** -- a self-signed cert, or an internal CA absent from the image, is the usual case. Such a deployment worked by accident before. **Migration: set `LITELLM_TLS_VERIFY=false` to restore the old behaviour.** Prefer adding the gateway's CA to the trust store; the master key travels on this channel, so the opt-out is worth reserving for a proxy on `localhost` whose certificate you issued.
- **On the ToC fallback the failure is SILENT, so do not wait for an exception to tell you.** `llm/toc_fallback.py` wraps each chunk's extraction in a bare `except Exception`: a TLS error is logged as a warning and, when the first chunk fails, the function returns `[]`. The caller gets an index with **no ToC entries**, no raised error and no flag on the result -- indistinguishable from a document that genuinely has no outline. This is the same silent-degradation class as an unroutable `DATASHEETINDEX_MODEL`. Client *construction* never fails, because it opens no connection; only the request does. So the observable symptom of a missed migration is not a crash but quietly worse navigation, on the 4-in-9 of documents whose ToC scores below threshold.
- **Deployments that embed this library need the variable set BEFORE upgrading, not after.** That includes the MCP server (`datasheetindex-mcp-server`): registration and tool listing are unaffected -- the LLM client is lazy -- but `build_datasheet` degrades as above. Verify rather than assume the certificate is fine: `httpx2.get(f"{LITELLM_BASE_URL}/health/liveliness", verify=True)` from inside the deployment image is the whole check, and an internal gateway fronted by a private CA fails it even though every browser on the corporate network trusts it.
- **Nothing else about the TLS surface changes.** The variable, its spellings, `LITELLM_TIMEOUT_SECONDS` and `LITELLM_MAX_RETRIES` are all as they were, and a deployment that already set `LITELLM_TLS_VERIFY` explicitly -- either way -- sees no difference.
- **This does not make the repository verify TLS everywhere, and one path is deliberately untouched.** `index._urlopen_with_ssl_fallback`, used when a datasheet is fetched from a URL, still retries any `ssl.SSLCertVerificationError` with `CERT_NONE` after logging a warning, and has no opt-out. That is PDF download from vendor sites with improperly chained certificates, not credential-bearing traffic, and it is out of scope here -- but do not read this entry as a repository-wide guarantee.
- **Installing `datasheetindex[llm]` now requires `openai>=3.5.0`.** A deployment pinning openai 2.x must move; there is no supported combination of this extra with the old major, because it is the openai version that decides which HTTP library the SDK is built on. Nothing in the library's own API changes -- `create_llm_client`, every `LITELLM_*` variable, and both optional client interfaces are as they were.
- **The default lock is now mcp 2.x, which inverts which major a plain `uv sync` exercises.** `claude-agent-sdk` 0.2.147 widened its pin from `mcp<2.0.0` to `mcp<3.0.0`, and with nothing left holding 1.x back the resolver takes 2.1.1. The `[mcp]` extra stays deliberately unbounded and `_build_mcp_server` still serves both APIs. **Both majors were verified for this release**: the full suite passes on the locked 2.1.1, and again on a throwaway environment pinned to `mcp[cli]<2` (1.29.1). The standing CI consequence is recorded in the repository notes -- the GitLab `eval-mcp2` job now re-tests what the default lane already covers, and it is 1.x that has become the unexercised branch.

## [0.34.0] - 2026-08-12

### Added
- **`regenerate_toc` makes the ToC quality gate appealable.** `build_datasheet(regenerate_toc=true)` -- and `DatasheetIndex.build(regenerate_toc=True)` -- forces the LLM ToC fallback regardless of the baseline's quality score, for a caller or agent that has read the outline and judged it unusable anyway. The gate was previously unappealable, and that was the real defect behind the score bug below: `get_artifact_manifest` already returns both `toc_quality` and the full `toc` tree, so an agent could see an outline of `Page 1`, `Page 2`, ... naming no section and had no way to act on it. `force_rebuild` is not that lever -- it only busts the cache, then re-runs the same deterministic scoring, gets the same number and reaches the same decision.
- **It is part of the artifact-reuse key, in memory and on disk**, for exactly the reason `DATASHEETINDEX_FURNITURE` is (0.33.0): it changes the **content** of the published artifact -- the ToC is reconstructed from body text instead of read from the PDF's bookmarks -- so an artifact built one way must not be served for a request that asked for the other. Without it, asking for regeneration after a normal build matched on version, source and options and served the stale ToC, with `json_sha256` agreeing because it hashes that same stale file.
- **It overrides the score comparison in `_accept_llm_toc_candidate`, and only that one.** An enumerated outline scores **0.680**, so requiring the replacement to beat the baseline would let the broken number veto its own repair. The other three guards still apply -- a non-empty candidate, the entry floor, and no page-coverage regression -- because they protect against a degenerate *candidate*, which an explicit request says nothing about.
- **Without credentials it raises rather than silently doing nothing.** Regeneration needs an LLM client; if none was supplied and none can be constructed, `build` raises `RuntimeError` naming the `[llm]` extra and the two environment variables. The check runs twice, deliberately: in `DatasheetIndex.build` for the Python API path, and again in `DatasheetTools.build_datasheet` *before* it removes the sidecar -- otherwise a call that cannot succeed would invalidate a perfectly good cached artifact on its way to failing. A tool that appears to ignore the parameter invites the agent to retry forever against it.
- **The tool description names the next action**, the convention `defs.py` already sets: it tells the agent that `toc` is the PDF's own outline, that it is occasionally useless, and that the answer is to call `build_datasheet` again with `regenerate_toc=true`. The parameter is in the tool's `input_schema` and not only in the Python signature -- an MCP host validates arguments against the schema, so a Python-only parameter is unreachable from the tool surface.

### Fixed
- **A missing LLM client no longer disables artifact reuse forever.** When the ToC gate fired and no client could be built, the build appended `toc_fallback_no_client` to `enrichment_notes`, which set `llm_enrichment_incomplete` on the sidecar, which made `reuse_blocker` refuse the artifact -- permanently, because rebuilding cannot create credentials. `[llm]` is an optional extra, so no-credentials is the *default install*, and a PDF with no usable bookmarks is ordinary: **2 of the 26 corpus documents** below have no ToC at all, score 0.00, and tripped this on every build. Such a document was re-indexed from scratch on every single request, forever, with nothing in the result saying why.
- **The fix is a `toc_fallback_pending` flag checked by the caller, mirroring `figure_captions_pending`.** The codebase already drew the distinction and already had the words for it: `llm_enrichment_incomplete` means a *transient failure worth retrying*, while pending captions are a *stable fact about the environment*, which `reuse_blocker` deliberately does not judge -- deciding on it requires probing whether capability exists now, which is I/O, and that function is pure by contract. A no-client ToC fallback is the second kind, and was being recorded as the first. The artifact is now reused as-is while no client exists and invalidated the moment one appears. `toc_fallback_raised` and `figure_caption_failed` stay transient; those are genuine failures.
- **The probe is `_VisionResolver.has_client()`, not the existing `get()`.** `get()` returns the vision-*filtered* client, and the ToC fallback needs any text client -- so reusing `get()` would have left a text-only deployment serving the stale artifact after the very credentials that could fix it arrived. Both gates ask it last, after every cheap check has already passed, so a real client is never constructed on a path that was going to reject the artifact anyway.

### Changed
- **A table of contents is now scored on whether its entries tell sections apart.** `assess_toc_quality` multiplies its weighted total by an informativeness factor, `distinct(normalize_key(breadcrumb or title)) / entry_count`; the four existing factors, their weights and `title_score` are unchanged. Without it the ranking was inverted, not merely imprecise: a fake `Page 1..20` outline scored **0.860**, *above* the bundled PSoC 6's real 89-entry outline at **0.820**, with `Page 1..134` at **0.680** and a single real section at **0.620**. **Raising the 0.300 threshold therefore cannot work** -- no cutoff separates two populations when the bad one ranks above the good one.
- **Repairing `title_score` instead was measured and rejected.** Its check rejects only *purely* numeric titles, so `"Page 1"` scores perfectly -- but forcing the whole factor to zero still leaves the enumerated outline at **0.48** (134 pages) to **0.66** (20 pages). Three of the four factors, 80% of the weight, measure whether the outline *spans* the document, and enumeration maximises all three by construction: one entry per page is a plausible entry count and perfect page coverage, and only depth suffers. A 20% component cannot pull a score across 0.3. That is why informativeness multiplies the total rather than joining it as a fifth weighted factor -- it is a precondition, not a contribution. An outline whose entries cannot be told apart cannot route a reader anywhere, however completely it covers the pages.
- **Keyed on the breadcrumb rather than the bare title, and the corpus says why.** Two chapters legitimately share a subsection name, and the pre-computed ancestry path separates them: bare titles against breadcrumbs score `esp32_trm` (784 pages) **0.727 against 0.995**, `raspi_rp2040` (642p) **0.744 against 0.943**, and `micro_atmega328` (294p) **0.794 against 0.955** -- up to 27 points on the large reference manuals, which are the repetition stress case. A flat `Page 1..N` outline has `breadcrumb == title`, so it still collapses to a single key and is still caught. `TocNode.breadcrumb` defaults to `""` on a directly constructed node, so the title remains the fallback. The normaliser is `core/furniture.py`'s `normalize_key`, reused rather than re-written; both modules are pure, so the import adds no coupling, and a comment above it now names this second consumer.
- **Validated on 26 documents from 7 vendors** (TI, Espressif, Bosch, Microchip, Raspberry Pi, Infineon, Vishay), 5 to 784 pages. **24 have a ToC and are scored**; the other 2 have none, already score 0.00 and already fall back. (ST, NXP and Analog Devices blocked scripted download and are absent.) **Fallback decisions that flip: 0** -- no document with a meaningful ToC is pushed below the threshold. The worst real document, `raspi_pico`, scores **0.697** against the 0.300 threshold, 2.3x headroom, while the best degenerate outline manages 0.043; that **16x** gap is what makes the rule safe, not the precision of the normaliser. The bundled PSoC 6 is unchanged at **0.820** with informativeness exactly **1.000**, pinned by a test so that a future change to `normalize_key` reintroducing collisions fails loudly.
- **The normaliser's real limitation, recorded rather than hidden: digit masking collapses legitimately numbered siblings.** `Port P# (P#.# to P#.#) Input/Output` x8 on `ti_msp430f5529` (Ports P1-P8, all distinct), `GPIOR# - General Purpose I/O Register #` x3 on `micro_atmega328` (GPIOR0/1/2), and `D.#. # June #` x5 on `raspi_pico` (different release dates). `ti_msp430f5529` pays **0.820 -> 0.741** for it. It is unfixable by inspecting titles alone -- `Page 1`/`Page 2` and `Port P1`/`Port P2` are structurally identical, differing only in whether the stem carries meaning -- and removing the masking is not an option either, since it is the entire mechanism. Accepted because the corpus bounds the damage: on real documents collisions are always a *minority* (worst measured **21%**, on `raspi_pico`), whereas a degenerate outline collapses essentially 100% of its entries.
- **No degenerate outline appeared in any of the 26 corpus documents.** The shape was observed on a real document earlier in development, but among mainstream vendor datasheets it is rare. This factor is cheap insurance against a demonstrably wrong gate, not a fix for a common case; `regenerate_toc` and the caching fix above are where this release's value is.
- **`recommend_summaries` widens as a consequence, accepted deliberately.** It is `score < 0.5 or entry_count > 40`, so a newly low-scoring document now recommends summaries too. Defensible -- a document with a useless ToC is one where summaries help -- but it is an LLM cost that follows automatically from the score change. The non-cacheable regression it would otherwise have caused for that same widened population is exactly what the reuse fix above closes, for the pre-existing population as well.

### Compatibility at a glance
- **`toc_quality.score` moves for any document whose ToC entries repeat.** Across the 24 scored corpus documents no fallback decision changes, and the largest drop measured on a real document is `ti_msp430f5529`'s 0.820 -> 0.741. A consumer that pinned an exact score needs adjusting. `TocQuality`'s fields are unchanged -- `score`, `entry_count`, `max_depth`, `page_coverage`, `recommend_summaries`, `details`; there is no new one.
- **What did change shape is the `details` string**, which gains a fifth clause: `entry_score=..., coverage_score=..., depth_score=..., title_score=..., informativeness=0.XX`. It is a `", "`-joined string with no keys to address, so a consumer that split it and indexed positionally is precisely the one that breaks -- there is nothing after `title_score` to shift, but a consumer counting the parts, or reading the last one, now gets a different answer. Parse it by the `name=` prefix, or do not parse it at all.
- **`details` is written to the build sidecar and deliberately omitted from the ToC JSON's `toc_quality` block** (`models.py`: `TocQuality.to_dict` serializes it, `index.py` does not). So the new factor is invisible to an MCP or Agent-SDK agent, which sees only `get_artifact_manifest`'s `toc_quality`. That is intentional -- the agent acts on `score` and on the `toc` tree itself, and `regenerate_toc` is its lever -- but it means the informativeness number is a *diagnostic for an operator reading the sidecar*, not a signal on the tool surface.
- **The version bump is load-bearing, and closes one specific window.** `datasheetindex_version` is a fingerprint field, so 0.34.0 invalidates every 0.33.0 sidecar. That matters in one direction only. Forward self-heals: an old sidecar carries `llm_enrichment_incomplete=True` and is rejected and rewritten. Backward does not: a **new** sidecar carries `toc_fallback_pending` with `llm_enrichment_incomplete=False`, and pre-change 0.33.0 code silently drops the unknown key, sees a clean record, and would reuse it forever without ever invalidating when a client appears. Sidecars written before and after this work would otherwise both claim `0.33.0`, so do not ship any of this without the bump.
- **`toc_fallback_pending` is read defensively when absent**, defaulting to `False` -- the same exception `figure_captions_pending` already has to the rule that a sidecar missing a field is a hard error. Neither is a fingerprint: a record written before the field existed is a valid record of a build that found no client, and defaulting reproduces exactly the reuse behaviour that artifact already had, where requiring it would log a diverged-shape warning on every pre-existing sidecar.
- **`regenerate_toc` is additive and defaults to `False` everywhere** -- Python signature, tool schema, and cache key -- so no existing call changes behaviour. It is **appended** to both `DatasheetIndex.build` and `DatasheetTools.build_datasheet`, in the same position on each, so a positional call written against 0.33.0 still binds every argument to the parameter it named. The one new failure mode is the deliberate one: passing it `True` without credentials raises instead of quietly returning the ToC you asked to replace.
- **Considered and rejected: a library-side LLM judge of ToC quality.** The agent already holds the full `toc` tree, so a second model call would pay to reach a conclusion the first model can draw for free -- and it would put nondeterminism inside a cached artifact. The score stays a cheap deterministic floor whose only job is deciding whether to spend one LLM call; judging is the agent's, which is what `regenerate_toc` is for.

## [0.33.0] - 2026-08-11

### Changed
- **The page-matched text file no longer carries running headers and footers.** Every page of a datasheet repeats a header naming the part and a footer with the document title, a revision string and a page number, and all of it reached `search_text`, `get_section_text` and the LLM ToC fallback. The cost was search precision rather than tokens: on the bundled PSoC 6, `search_text("PSOC")` returned 209 matches -- over the 200 cap an agent sees, so genuine hits were evicted -- of which 133 were the header, and `Datasheet` returned 138 of which 133 were furniture. Those now fall to 76 and 6. The text file shrinks 200,584 -> 193,020 characters (3.8%, ~1,891 tokens) across 265 dropped blocks. The header *block* is gone from all 133 pages that carry it, but the string is not extinct: `PSOC™ 62 MCU` still occurs twice, in genuine body prose, and `002-23185 Rev. *S` still occurs once, because page 1's footer merges a legal-pointer sentence into a unique 142-character block that cannot reach the recurrence threshold -- the design failing safe, not a miss.
- **Detection is native PyMuPDF, on the default lane, with no new dependency.** A block is dropped when it lies wholly inside the top or bottom 20% of its page, is at most 200 characters, does not open with a caption keyword, and its whitespace-collapsed digit-masked text -- which must contain at least one letter -- recurs on at least `max(3, ceil(0.5 * pages))` pages. This is a simplified Lin page-association (SPIE 2003) -- the standard method, not a new one.
- **A key that dominates one page parity is furniture too, which is what makes alternating headers detectable.** Many datasheets alternate the header and footer between odd and even pages, so each variant lands on just under half the document and neither reaches `ceil(0.5 * pages)`. Measured on a 17-document, 8-vendor corpus: `micro_atmega328.pdf` (294 pages) has four genuine furniture keys at **exactly 146 pages each** -- `ATmega328P [DATASHEET]` on 146 even pages and none of the odd, its twin `3 ATmega328P [DATASHEET]` the mirror image -- one page short of the 147-page threshold, so the document stripped **nothing at all**. A key now also qualifies when, within one parity's own bucket, it clears `max(PARITY_MIN_PAGES, ceil(0.5 * bucket))` **and** appears on at most `PARITY_DOMINANCE * that count` pages of the other parity. The letter requirement, the position band, the size limit and the caption guard are unchanged and apply to both routes.
- **Dominance, and not a bare per-parity threshold, is what keeps that from being a blanket loosening.** A parity bucket is half the document, so a bare per-bucket threshold would admit any key recurring on roughly **25%** of the pages -- exactly the range the 0.5 fraction was measured to reject, where the PSoC starts losing the running section heading `6 Electrical specifications` (47 of 134 pages). Requiring near-absence from the other parity narrows the new route to the actual signature of an alternating header. `PARITY_DOMINANCE = 0.2` is not a tuned value: every key the route recovers on the corpus is a clean split (146/0, 0/146, 14/0, 0/13), so dominance rejects none of them. It has exactly one measured cost, recorded rather than hidden -- `www.ti.com` on `ti_lm358.pdf` is 22 pages of one parity and 8 of the other, genuine furniture that dominance declines, because 8-against-22 is an uneven recurrence rather than an alternating layout and any rule loose enough to admit it admits every similarly uneven key. That is a miss, the direction this design fails in everywhere else.
- **The parity route floors higher than the overall one, at `PARITY_MIN_PAGES = 6`.** `MIN_PAGES = 3` is absolute and does not scale, so a parity route sharing it collapsed on mid-length documents to "3 pages of one parity, none of the other": on a 10-page document, where the overall route demands 5 pages, a key on pages 3, 5 and 7 was returned as furniture -- 30% of the document, and at 13 pages it fired at 23%. Dominance is *weakest* precisely there and cannot cover for it, since `0.2 * 3` is 0.6 and forces the other-parity count to zero, which any three-page odd-only run satisfies trivially. Odd-page section starts are a standard print convention, so the document that breaks it is ordinary rather than contrived, and the string the example deleted was `Register description` -- the very content the 0.5 fraction is documented as protecting. Closed rather than documented, because deleting real content is the one outcome this feature may not have. Doubling the floor cannot bind where the route earns its keep: the recovered keys clear their bucket thresholds by 146-against-74 and 14-against-10, and every recovered key and character count on the corpus is unchanged by it.
- **Measured recovery, and the documents that did not move.** Counted in dropped **blocks**, through the same `_is_furniture_block` predicate the text path uses: `micro_atmega328.pdf` 0 -> 584 blocks and 0 -> 13,034 characters (1.9%); `ti_ina219.pdf` 55 -> 109 blocks and 1,034 -> 4,914 characters (1.3% -> 6.2%); `tcan1044a-q1.pdf` 48 -> 101 blocks and 1,200 -> 4,957 characters (1.7% -> 6.9%). The other **14** documents in the sweep, including the bundled PSoC 6 at its unchanged 265 blocks, are byte-identical: the parity route adds nothing to a document the overall threshold already handled. A content-shaped-removal check over every dropped **line** stays at **zero** across all 17, before and after. (One block is typically several lines -- the PSoC's 265 dropped blocks are 926 lines -- so block and line counts must never be quoted under the same word.)
- **A furniture key must carry at least one letter, so a page-number-only footer is deliberately not stripped.** Digit runs are masked to `#` to make a page number match across pages, which means a key can end up with no lexical evidence at all -- `#`, or `#.# #.#`. A bare page-number footer, an extremely common datasheet layout, then makes `#` furniture, and every bare-number block in either band is deleted document-wide. Reproduced on a 10-page synthetic: `120`, `127` and `3.3 4.3` were removed from genuine table rows, and no other guard helps, since such blocks are short, in-band and carry no caption keyword. Requiring a letter converts a content-deletion mode into a miss, which is the direction this design fails in everywhere else. It costs nothing measurable: **zero** furniture keys on either bundled PDF and on all 16 keys of the seven-document survey, because a real footer carries a title, a revision or a URL alongside its numbers (`# V#.# #-#-#` still qualifies). The test uses `str.isalpha`, not `[A-Za-z]`, so a non-Latin script counts as evidence.
- **`Table N` captions are safe by construction.** An earlier line-level design would have deleted them -- `Table #` recurs 89 times on the PSoC, but that is a *line*-level count. What actually keeps captions is **block granularity**: `Table 43` is a body block and never enters the edge band, so the recurrence rule never sees it. The caption-keyword rule is insurance behind that, not the active mechanism -- worth keeping because `figures.caption_entries` reads the stripped text and `TocNode.continued_tables` is built from `Table N (continued)`, so the cost of being wrong is high and the cost of the guard is nil.
- **The preamble is unchanged, byte for byte.** `preamble.py` reads `_extract_page_text`, which stays unstripped; the stripping lives in `scan_pages`. The documented "raw text, zero heuristics" contract still holds, with no flag and no second code path.
- **`extract_table_markdown`'s description was corrected.** 0.32.0 told the agent "the page's running header and footer are omitted; **get_section_text still has them**", which this release makes false -- `get_section_text` slices the stripped text file. It now reads "omitted, as they are in get_section_text and search_text". It is text the agent reads and reasons from, so a stale sentence there is worse than none.

### Added
- **`DATASHEETINDEX_FURNITURE=0`** disables stripping entirely (also `false`, `no`, `off`), matching `DATASHEETINDEX_PARALLEL`'s spellings and its reasoning: an escape hatch that ignores `=false` looks broken to whoever most needs it. It is part of the artifact-reuse key, in memory and on disk, for the same reason the two model knobs are: it changes the **content** of the published text file, so without it a rebuild with the hatch flipped served the stale artifact and `text_sha256` still matched -- it hashes that same stale file. The key records the resolved boolean, not the spelling, so `0` and `off` share one artifact.
- **`core/furniture.py`**, a pure module with no PyMuPDF, no environment and no I/O, so the decision logic is testable without a PDF.
- **An ONNX-oracle precision test.** `pymupdf.layout` classifies `page-header`/`page-footer` directly but costs ~0.95s/page against an ~8s build and sits behind the optional `[layout]` extra, so it cannot serve the text path -- but it makes an independent cross-check. Blocks we drop are asserted to be furniture by the model at >= 0.95 precision. Recall is reported only: we knowingly detect less than it does.

### Compatibility at a glance
- **The text file changes** for any document with running furniture; that is the point. Page markers, page ranges and section boundaries are untouched, so `get_section_text` and page alignment are unaffected, and the figure index keeps its per-page ordering. `artifact_cache` fingerprints on the version, so stale text files invalidate automatically.
- **Not detected, by design:** furniture whose *letters* vary per page, such as a per-chapter running title; furniture that recurs **unevenly** rather than alternating, which the parity route's dominance rule declines (`www.ti.com` at 22-versus-8 on `ti_lm358.pdf`); furniture confined to one *part* of a document, such as the 32-page LM358 datasheet proper bound ahead of 36 pages of package-option and mechanical appendices, where each header variant reaches 16 of its parity's 34 pages and neither the overall nor the parity threshold is met; and footers consisting only of a page number, which carry no letters (above). All fail safe by keeping text. Lowering the threshold to reach any of them was measured and is worse -- at 0.33 the PSoC starts losing `6 Electrical specifications`, a running section heading.
- **The one shape that would still be deleted wrongly** is a table header row repeated on more than half the pages of a table-heavy datasheet: it is in-band, caption-free and recurrent, which is the whole rule, and there is no cheap guard against it. Measured on the PSoC, the repeated `Spec ID# Parameter Description Min Typ Max Unit Details/conditions` row reaches 38 of 134 pages -- below the 67-page threshold there, but that margin is a property of that document, not of the design. `DATASHEETINDEX_FURNITURE=0` is the escape hatch if it is ever hit.
- **A cover-page title can be caught in the same net as the header it resembles.** On page 1 of the bundled PSoC 6, the product-title block `PSOC™ 62 MCU` is dropped, because the same string also runs as a header on most other pages and block-level detection cannot distinguish "this page's title" from "every page's header" when the text matches. The string remains reachable through the preamble, which is deliberately unstripped, and through `search_text`.
- **Considered and rejected:** an existing library (the only zero-dependency candidate, `refinedoc`, deletes `Table N (continued)` captions because it works on text lines with no coordinates) and LLM-driven detection (cheap, and higher recall, but on tcan1044a-q1 `qwen3.6-27b` flags 73 of 198 candidates including a table header row and several section headings -- and the text file must build without credentials). Both are recorded in the design spec.

### Changed

## [0.31.0] - 2026-08-07

### Fixed
- **One unresolvable PDF bookmark no longer aborts the whole index build.** PyMuPDF's `get_toc()` reports `-1` for any outline entry whose destination it cannot resolve -- a property of the PDF, not of the caller -- and `build_tree` handed every entry to `validate_toc_entry`, which raises on `start_page < 1`. There was no way to recover from outside: `raw_toc` is read inside `index.build()`, and neither `DatasheetIndex.build()` nor `DatasheetTools.build_datasheet()` exposes a tolerance knob, so a consumer could only catch the exception after the whole build was already lost. Seen in production against 0.21.0: **11 build failures and 14 downstream errors across 4 comparison runs** in `datasheet-agent`, every comparison that ran in that window.
- **The cascade was the real cost.** Each `RuntimeError: No datasheet artifacts available` followed a failed `build_datasheet` by 1-5 seconds -- not an independent fault, but the agent trying `get_section_text` and `search_text` against an index that could never be built. The retries are deterministic re-failures, so the model burned turns and then answered the extraction from whatever it could reach without the document. That is the ungrounded-answer failure mode, reached through a document the library simply declined to index.
- **`build_tree` now drops an out-of-range entry and names it in a WARNING.** Four decisions, deliberately: **drop, do not clamp** -- the precedent 0.23.0 set for the LLM path, where a plausible-looking wrong page is worse than a missing section; **bound both ends** -- `start_page > total_pages` is the same corruption class and the more dangerous one, because `compute_end_pages` derives a node's `end_page` from its *next sibling's* `start_page`, so a bookmark past the end makes the preceding section swallow the document, and neither path had an upper bound before; **keep descendants of a dropped node**, since each child carries its own valid page and losing real sections is the worse failure -- the child re-parents onto the surviving ancestor via the existing stack, so its breadcrumb changes while its page range stays correct; and **leave `validate_toc_entry` raising**, so the strict contract stays available to anyone validating an entry on its own. Shape and level errors still raise from `build_tree` too: those are caller errors, not properties of the document.
- **An all-invalid ToC now returns `[]` rather than raising**, which is what lets `index.build` fall through to the LLM ToC fallback -- the designed recovery for a document with no usable bookmarks. Before, such a document could not reach it.
- **This was not the 0.23.0 fix.** That one hardened `toc_fallback._drop_unsupported_entries` on the **LLM** path (`b8db57e`), which is where the drop-don't-clamp precedent comes from. This is the **native PyMuPDF bookmark** path: `index.py` calls `extract_toc(doc)` then `build_tree(...)` with no guard between them. Reproduced on 0.30.0 before the fix, and the six regression tests were confirmed failing first -- five of them, with the sixth passing on the old code to pin the validator contract that must not change.

### Added
- **`toc_source` says where the table of contents came from.** `"pdf_outline"` (the document's own bookmarks, so the page numbers are exact), `"llm_reconstructed"` (the bookmarks were missing or too weak and the ToC was rewritten from body text, so every `start_page` is an inference from a `--- PAGE N ---` marker), or `"none"`. It sits beside `toc` in the ToC JSON, on `DatasheetArtifacts`, and in the manifest `build_datasheet` returns.
- **`toc_quality` could not answer this, and that was the gap.** It scores the tree that came out, not who wrote it: a reconstruction that scores well and a good outline are the same number. The provenance was previously visible only as a log line, so a consumer holding the artifacts -- or an agent holding the manifest -- had no way to tell that a `start_page` was inferred rather than read. The two call for different handling of the same field, so they are now reported separately.
- **A rejected fallback candidate reports `pdf_outline`.** The field names the tree you were given, not whether the fallback ran -- the same distinction `llm_enrichment_incomplete` already draws, where a rejected candidate is a completed decision rather than a degraded build.
- **The agent is told what to do with it.** `build_datasheet`'s description now says that `llm_reconstructed` means confirming a section with `search_text` before reading a range from it. A signal computed so the agent can judge what to trust, that the agent never sees, does no work -- the manifest is the only thing an MCP consumer is handed.

### Changed
- **All dependencies upgraded**, including the only runtime one: **pymupdf 1.28.0 -> 1.28.2** (and `pymupdf4llm` / `pymupdf-layout` to match). Full suite green on the new pins.
- **`parse_toc_entry` is split out of `validate_toc_entry`.** It checks an entry's shape and level and returns the raw `start_page`, leaving `build_tree` to decide what to do with a page it cannot use. `validate_toc_entry` is now that function plus the strict page check, so its behaviour is unchanged for every caller.

## [0.28.0] - 2026-08-05

### Fixed
- **Figure captioning no longer loses roughly half its captions on any model the gateway does not serve natively.** `describe_image` sent its request over the **Responses API**, which on an OpenAI-compatible gateway is a *bridge* for non-native models -- and that bridge can file the model's answer as a `reasoning` item carrying `reasoning_text`. `output_text` concatenates only `output_text` chunks, so the caption came back as the empty string with its own text sitting in the same response payload. Measured with the shipping client against a self-hosted `qwen3.6-27b` (vLLM) over 16 real figure regions from the repo's own PSoC 6 and TI PCN fixtures: **8 to 12 of 16 captions empty** over five runs, with a **different subset each run** -- per-call sampling, not a property of any figure. It is invisible in the artifact except as absent captions, which is why it had to be measured rather than reasoned about.
- **The severity is a poisoned cache, not just thin captions.** `caption_figures_in_place` scores a blank reply as `failed`, which marks the artifact incomplete -- so a transport that fails half the time would re-caption the document on **every future build, forever**. That is precisely the outcome the `blank` / `failed` / `pending` split was introduced to prevent, reached through a channel that split does not see.
- **The fix is Chat Completions, which bypasses the bridge rather than working around it.** Same model, same images, same prompt: **0 empty in 144 calls** across nine runs, and the raw message carries no reasoning channel at all (`message` keys are `content`, `role`, `provider_specific_fields`). Reading the reasoning item back on the Responses path was considered and rejected: it would make the caption depend on the model's *thinking* channel happening to contain a clean answer, which is luck, not a contract.
- **One transport for every model, not a branch on model name.** gpt-4.1 -- the default, and the only model this call has ever shipped against -- was re-measured over the same 16 regions on Chat Completions and is indistinguishable from the Responses path: 1084 median input tokens either way, 0 empty, 94 vs 91 median output tokens. That token figure doubles as the check that `detail: "high"` survives the move; `"low"` would show as roughly a tenth of it, and `"low"` is the setting a previous release proved produces confident fabrication of table rows. Note the request forms are **not** interchangeable: `image_url` is a plain string on Responses and an object (`{"url": ..., "detail": ...}`) here, and the wrong one type-checks and then fails at the gateway.
- **Text calls are untouched.** `__call__` and `structured_json` -- the ToC fallback and summaries -- still use the Responses API. They are reachable by the same bridge behaviour (a short text answer was observed landing in `reasoning_text` too), but nothing shipping today points them at a bridged model, and moving them means mapping `text.format=json_schema` onto `response_format` against gateways whose schema support is not uniform. Deferred deliberately, not overlooked: **do not point a non-native model at summaries or the ToC fallback until that work is done.**

### Added
- **`DATASHEETINDEX_VISION_MODEL` selects the model for figure captioning alone.** Unset -- the default -- captioning follows the same model as summaries and the ToC fallback, exactly as before, so this changes nothing for an existing install. It exists because captioning is the only per-figure cost in a build, capped at 20 calls per document, and the cheapest capable vision model is a property of a **gateway**, not of this library. The self-hosted model that motivated it meters at $0 input / $0.1321 per MTok output against gpt-4.1's $2 / $8 -- roughly 250x cheaper per document -- at caption quality a side-by-side over 16 real regions found competitive (on one AMUX block diagram it named `shield_pad`, `vref_ext`, `csh` and `cmod`, which gpt-4.1 missed; on one qualification table it mislabelled the column headings gpt-4.1 got right). A setting rather than a new default because that model is absent from its own gateway's staging tier and meaningless to anyone pointing `LITELLM_BASE_URL` elsewhere -- a hardcoded alias would break both to save one line of configuration. Empty and whitespace-only values are treated as unset, since that is what a commented-out `.env` line or an absent ConfigMap entry leaves behind.
- **The caption call now caps output at 300 tokens (`VISION_MAX_TOKENS`).** Prompt compliance is not uniform across models: over the same 16 regions the median reply is 71-102 tokens and gpt-4.1's worst case is 197, but qwen answered a 128-pin TQFP pinout by enumerating all 128 pins -- 667 tokens against gpt-4.1's 134 on the same image. Truncation is not a new failure mode here; the caption prompt already orders its output for it ("your text may be truncated, so identifying labels must come before any description of structure"), so a clipped caption keeps the part that earns its place in the digest. The cap sits above every compliant answer measured, so it binds on runaways only.
- **An empty caption is no longer silent, which is the reason this bug needed a measurement campaign to find.** A raising call was always logged; an empty *reply* was not, and both reach the artifact as the same `figure_caption_failed` note. The transport fix does not retire the failure *class*: a well-formed 200 carrying no text survives any future gateway, model or SDK. One log line turns the next instance into a grep.
- **The output cap is `max_tokens`, and the alternative was measured rather than assumed.** `max_completion_tokens` was considered; through this gateway **both spellings are accepted by every model tested** -- gpt-4.1, the self-hosted qwen and gpt-5-mini all answered under either -- so the newer name buys no compatibility while `max_tokens` is the one an OpenAI-compatible backend such as vLLM is certain to know. Raising the cap to accommodate one reasoning model would raise the per-figure input cost for every other.
- **`DATASHEETINDEX_VISION_MODEL` is part of the artifact cache key, so switching it rebuilds rather than serving the previous model's captions.** It changes what is in the artifact, and `model` -- the other thing that does -- has always been keyed; without it, pointing captioning at a different model reused the old captions from disk in silence. Found by direct verification rather than by review, and it is not reachable from a source tree -- on-disk reuse is disabled for an editable install, so reproducing it required simulating a real one. **No extra rebuild cost on upgrade:** `reuse_blocker` already invalidates every artifact whose recorded version differs from the running one, so 0.28.0 rebuilds once regardless. The **env value** is recorded, not the resolved model: when it is unset the vision model *is* `model`, which the key already carries, so recording a resolved default would key the same fact twice and drift when the default moves.
- **An empty `choices` list returns an empty caption instead of an `IndexError`.** A content filter or an upstream error envelope can produce a well-formed 200 with no choices. The caller already degrades an empty caption to a failed call; the exception would instead surface a traceback whose text has nothing to do with captioning.
- **A live regression test with enough calls to see a coin flip.** A single live call passes half the time on a broken transport, which is worse than no test, so `test_describe_image_never_returns_an_empty_caption_over_repeated_calls` makes six -- 1 in 64. ### Fixed
- **PyMuPDF's layout advertisement no longer lands on the stdio server's JSON-RPC wire.** `find_tables()` calls `pymupdf._warn_layout_once()`, which `print()`s "Consider using the pymupdf_layout package..." to **stdout** -- the channel the stdio transport carries JSON-RPC on -- once per process, unless the `[layout]` extra is installed. It also cannot affect the internal registry entry, which installs `datasheetindex[llm,mcp,layout]`: with `pymupdf.layout` importable the notice never fires at all. The regression test therefore reads to EOF *after* the process exits; one that only checked the responses it asked for would pass while the wire was corrupt. It fails on 0.27.0 with `non-JSON written to the stdio wire: ['Consider using the pymupdf_layout package...']`.

## [0.26.0] - 2026-07-26

### Changed
- **The `preamble` is now page-marked, larger by default, and says what it dropped.** It carries `--- PAGE N ---` markers in the same format as the page-matched text file, so every line is attributable and citable; `generate_preamble` gains `max_pages` alongside `max_chars`, both keyword-only on the new `build_front_matter`, and the character default rises from 2400 to 5000. The old default was not merely small, it kept the wrong half: measured on the PSoC 6 (CY8C62x8), pages 1-2 hold 4746 characters of page text (4747 as the old code's newline-joined string) and 2385 were emitted, and because a character budget applied in document order retains whatever sits earliest, the emitted text ended on page 1's legal footer -- "Please read the sections 'Important notice' and 'Warnings' at the end of this document" -- while page 2's "13 run-time configurable serial communication blocks (SCBs)", thirty-two TCPWMs, "12-bit 2-Msps SAR ADC" and "Up to 102 programmable GPIOs" were dropped. At 2400, 19 of the 21 documents in the corpus below would be cut, so truncation was the normal case at the old cap, not an edge case. **The new default is measured on 21 documents** -- 14 datasheets and 7 product-change notices, 1047 pages, six vendors (Diodes, Infineon, Microchip, Nexperia, onsemi, TI) -- and it does not fit everything: **13 of the 21 fit whole and 8 are cut.** The 8 are six of the seven TI datasheets, whose pages 1-2 run 5332-7404 characters, and two of the four onsemi PCNs (5156 and 6309); between 170 and 2424 characters fall past the cut. Of the 13 that fit, the widest is the PSoC 6 at 4746 characters, using 95% of the budget (TLE9350BSJ, 30 pages, 2554 / 2554; PSoC 6 CY8C62x8, 134 pages, 4746 / 4746; TI PCN 20251008002.1, 7 pages, 2688 / 2688 -- plus 107-109 characters of framing, or 232-234 with a truncation note). **5000 stands for what it keeps, not in spite of what it drops.** On the cut documents the general description and the features list are inside the budget, and what falls past it is page 2's table of contents, revision history and copyright footer -- on the TPS54331, `Updated the inductor current equations for IL(RMS) and IL(PK)` and `Product Folder Links: TPS54331`. Two exceptions worth naming: the MSP430F5529 also loses the tail of its general description and its Device Information package table, and the onsemi IPCN26979Z loses the continuation of a qualification-test table. Neither is silent -- the character note names the cut, and `max_chars` is the caller's to raise -- and raising the default to cover them would spend every document's budget on the tail of a few.
- **Truncation is disclosed rather than silent**, per the 0.18.0 principle that silence is not a completeness claim. Each cap gets its own `=== NOTE: ... ===` line because the extractor's knowledge differs between them: `max_chars` knows the total on the pages it read (at the old cap the PSoC 6 now reports `preamble truncated at 2400 characters; 2386 of 4746 characters from pages 1-2 shown, ending mid-page on page 1`), while `max_pages` knows only that later pages exist (`preamble covers pages 1-2 of 134; later pages were not examined`) -- it deliberately does not claim front matter continues, or count characters it never extracted, since reading one page past the limit to describe what was skipped would defeat the limit. Both fire when both caps bite, character note first. A page whose text does not fit at all is left out entirely, marker included: `--- PAGE 2 ---` with nothing after it would read as "page 2 holds no text", a claim about document content an exhausted budget does not license, and the cut in that case landed on the page boundary, so the note names no mid-cut page. A genuinely blank page still gets its marker. `max_chars` must be `>= 0`; a negative value used to be quoted verbatim as `truncated at -50 characters` and now raises `ValueError`, matching the existing `max_pages` guard.
- **Compatibility: `max_chars` now bounds document text, not the returned string.** Markers and notes are tool framing; counting them against the budget would make the amount of *content* a caller receives depend on how long the framing happens to be, and it is circular besides, since a note names the truncation point. The framing is exact after the fact (`len(text) - chars_shown`, both returned) and, for markers alone, exact before it: `sum(13 + digits(n) for n in 1..P) + (2 * P - 1)`, which is 31 at `max_pages=2`. Note lines are measured at 77 characters (the page note) and 124 (the character note) on the PSoC 6 -- roughly 100 each is an estimate, not a bound, since they embed page numbers and counts. Two existing tests asserted the old whole-string guarantee and are rewritten against `chars_shown`. Page text is also no longer `rstrip`ped, which is what makes the marker formula hold exactly; trailing whitespace before a marker is invisible in practice. A consumer treating the preamble as opaque prose is unaffected; one parsing it line by line now sees marker lines. `datasheet-agent` was checked and does not parse it.

## [0.25.0] - 2026-07-26

### Added
- **The ToC JSON gains two additive top-level keys, `figures` and `figures_excluded`.** `figures` is a page-then-position ordered list of two kinds of entries: `"raster"` (an image XObject placement, with `region` normalized `0.0-1.0` and clipped to the page, `bbox` in raw PDF points, `pixels`, and `page_area_pct`) and `"caption"` (a `Figure N` / `Fig. N` mention recognized in the column-aware page text, with a string `figure_number` -- never an int, since section-relative numbers like `"10-1"` are not arithmetic values). The two kinds are never merged into one entry, even when a raster region and a caption appear on the same page -- proximity-based association is deliberately out of scope. `figures_excluded` reports `{"below_min_area_pct": int, "min_area_pct": float}`: placements smaller than `min_area_pct` (a module constant, currently 1.0) are dropped from `figures` but counted here, so a vendor logo repeated across every page does not pollute the index. Both keys are always present, including `figures: []` on a document with no raster content, so their presence distinguishes "none found" from "predates the feature." Existing keys and both deliverables' other bytes are unchanged; the fold that produces this list into the existing text-extraction pass measured as noise (median 8.61s vs 8.65s across three runs each) on a 134-page datasheet, not a measurable regression.
- **Raster figure regions are now named by a vision model, on by default.** `build()`, `build_datasheet()`, and `build_batch()` gain `caption_figures: bool = True` and `max_figure_captions: int = 20`. When a vision-capable client is available -- supplied explicitly, or self-created the same way the ToC fallback already is -- every `"raster"` entry in `figures` at or above `min_area_pct` becomes a candidate for a short VLM description (`caption_source: "llm"`), ordered by visible area descending and capped at `max_figure_captions`; a third top-level key, `figure_captions_excluded`, discloses `{"above_max": int, "max_figure_captions": int}` on every build. There is no triage -- every candidate is captioned, including ones a text-layer caption may already name, because no cheap signal reliably tells the two apart (measured and rejected: matching per-page caption/raster counts, and thresholding page text density). A caption call that raises or returns empty leaves `caption` null, logs a warning, and marks the artifact `llm_enrichment_incomplete` so a transient gateway failure is never cached as a permanent absence; a document with no vision client available reuses indefinitely instead, and rebuilds with captions the moment credentials appear. `max_figure_captions` must be an integer `>= 0`, enforced at every entry point (`build()`, `build_datasheet()`, `build_batch()`, the CLI, and the tool schema) -- a negative value would silently slice from the end of the candidate list rather than cap it. Rendering is serial (PyMuPDF is not thread-safe for concurrent page work); dispatch to the VLM is concurrent, 4 workers, since it is pure network I/O. Live-measured on the 134-page PSoC 6 datasheet at the default cap of 20: serial dispatch took ~119s (about 6s/call), 4-worker concurrent dispatch ~13s -- both real numbers from the internal LiteLLM gateway, not estimates.
- **Compatibility: `caption_figures` defaulting to `True` is a behaviour change, not an addition.** `figures`, `figures_excluded`, and `figure_captions_excluded` are purely additive top-level keys -- no existing key changes, and no existing call site needs to change to keep building. But a caller that already supplies, or already has environment credentials for, a vision-capable client will now issue up to `max_figure_captions` VLM calls on a document's first build -- 20 calls on a document with 20+ candidate regions. What bounds it: the deterministic index is byte-identical either way, the cap is a hard ceiling the caller controls, disk reuse charges the cost once per document rather than once per build, and `caption_figures=False` or `max_figure_captions=0` restores the previous behaviour exactly, with no other cost.
- **`build_datasheet`'s manifest carries a bounded `figures` digest.** The MCP / Agent-SDK agent is handed the manifest and nothing else, so without this the consumer the figure index was built for never learned raster content existed -- it could read `json_path` off disk, but nothing told it to, and per the documented WSL namespace gotcha the server's filesystem may not even be the agent's. The new key is a digest, not a copy: `total` / `raster` / `captioned` counts, plus a `pages` list of `{page, figures, caption}` rows in ascending page order, one row per page holding figures, carrying that page's entry count and its largest-area caption (see the "Changed" entry below for why largest-area, not first). It is bounded by constants rather than by the document -- at most 40 rows, each caption clipped to 350 characters, with `pages_with_figures` and `truncated` disclosing what was dropped -- because the manifest is returned on *every* build and a scanned datasheet can hold one full-page raster per page. Full detail, including each region's normalized coordinates for `inspect_page(region=...)`, stays in the ToC JSON. The key is always present, so `"total": 0` is distinguishable from an artifact predating the figure index, and the digest is identical whether the build was fresh or served from either artifact cache gate. The `build_datasheet` tool description now names it and tells the agent what to do with it; it previously mentioned figures only as a cost warning.
- **`search_text` now discloses its own blind spot, and nudges on the miss rather than only in its description.** The figure index exists because a term rendered as pixels is unfindable in the text layer, but nothing told an agent that at the moment it mattered: the observed failure is an agent running one `search_text("SUMITOMO")`, getting `[]`, and reporting that the document does not contain the word -- while it sat 13 times in a raster supplier table two tool calls away. Two changes, deliberately paired. The tool *description* now carries the limitation and the remedy together ("the absence of a match does not prove the document lacks the term ... check the `figures` digest from `build_datasheet` ... then read it with `inspect_page`"), since a limitation stated without a next action just stops the agent. And because a description is read once, pages of transcript before the search that trips over it, an empty result now also carries a `note` field repeating the remedy inline. The note is deliberately narrow: it appears **only** when the search returned nothing **and** the document holds at least one `"raster"` figure entry (new `DatasheetTools.has_raster_figures()`). A document whose `figures` array holds nothing but text-layer `"caption"` entries gets no note -- those words *are* searchable, so there is nothing hidden and pointing at `inspect_page` would waste a turn -- and a search that found hits gets no note either, since a banner on every successful call is noise the agent learns to read past. Verified live against the TI PCN: `search_text("SUMITOMO")` returns `[]` **with** the note; `search_text("Compound")` returns 4 hits with none.
- **Compatibility: a keyless build still runs no summaries, figure or no figure.** Captioning made `build()` self-create a client whenever a document has candidate raster regions, which is a second construction site for a client the summaries branch also reads. Summaries are therefore gated on the client's *provenance*, not on one merely existing: `include_summaries=True` with `llm_callable=None` produces summaries only when the weak-ToC fallback created a client for its own reasons, exactly as in 0.24.0 -- a client created purely to caption figures does not enable them. Without this, inserting one image into an otherwise unchanged document would have turned a keyless `include_summaries=True` build from a no-op into one LLM call per ToC section, unbounded by `max_figure_captions` and disclosed nowhere, and would have added a raising path (`add_summaries` has no error handling) to builds that previously always succeeded. Captioning on the keyless path is unaffected, which is the whole point of its default-on design.

### Changed
- **The agent tool definitions are rewritten shorter, with argument guidance moved onto the arguments.** The five descriptions fall from 5750 characters to 2900 (`build_datasheet` alone from 3094 to 1222), on one rule: a description answers when to call the tool and what comes back, and everything about a parameter lives in that parameter's JSON Schema `description`. Twelve parameters that had no description at all now have one, including `pdf_source`, `output_dir`, `force_rebuild` and the model list that stops an agent inventing a gateway model name. Nothing was dropped -- the text moved -- so the full serialized surface falls 8389 to 7000 characters; the win is that a reader scanning one argument no longer reads five paragraphs about the others. Emphasis markers are gone (`IMPORTANT` x4, `CALL THIS FIRST`, `Do NOT` x2): Anthropic's Claude 4.5/4.6 guidance is that language written to stop older models *under*-triggering now makes these models *over*-trigger, and ordinary prose is the fix. `build_datasheet` also loses its copy of the raster-blindness warning, which now lives on `search_text` and on the empty-result note where the agent actually meets it. Three tests hold the line: every description is under a per-tool length budget, every parameter carries a description, and no description contains an emphasis marker -- all three fail against the previous text (4 of 5 over budget, 12 undocumented parameters, 3 markers). Behaviour checked live rather than assumed: given an empty `search_text("SUMITOMO")` beside a figures row naming a supplier table, the old and the new surface both chose `inspect_page(page=5, detail="medium")` on 3 of 3 trials.
- **A picture placed on many pages is now captioned once, not once per page.** Raster entries gain an `xref` field -- the image XObject the placement draws -- and the captioning pass groups placements by it: the largest placement of each distinct picture is rendered and described, every placement in the group receives that caption, and `max_figure_captions` bounds *pictures*, which is what "each captioned figure is one VLM call" always claimed it bounded. This is exact rather than heuristic: a PDF XObject's content cannot vary between placements, only its scale, so sharing one description across them cannot be wrong. Found by running the feature against seven public product-change notices: on onsemi's PCNs the only region above the area threshold is the header logo, so a four-page notice spent four VLM calls describing one logo four times, in four slightly different wordings. Measured after the change: the PCN corpus drops from 21 calls to 14 (33%), and across all nineteen corpus documents 9 of 86 candidates (10%) were repeats. No page goes dark -- the same 21 entries carry a caption before and after, now identical wherever the picture is -- and freeing cap slots lets more distinct content through (`ti-tlv9061`'s `above_max` falls from 9 to 8). An `xref` of 0 or missing means the document reported no identity, and such entries **never** group: treating unknown as equal would hand one picture's caption to every unidentified figure. `CaptionOutcome` gains `shared` (extra placements that received an already-earned caption) and documents that its fields are in two different units -- `captioned`/`pending`/`blank` count pictures, `shared`/`excluded_above_max` count entries, the latter because `figure_captions_excluded.above_max` is published in the artifact and answers "how many figure entries lack a caption". `get_image_info(xrefs=True)` costs nothing measurable: 0.93s vs 1.26s on the 294-page ATmega328P, 1.51s vs 1.66s on the 99-page TLV9061. **Test-fixture consequence worth knowing:** PyMuPDF folds identical image bytes into one XObject, so the suite's `_doc_with_images(3)` had been building one picture placed three times, not three pictures -- the fixtures now vary each pixmap's colour, and a fixture that reuses one pixmap is now testing the dedup path whether or not it means to.
- **Figure captions now name row and column labels, sent at `detail: "high"` instead of `"low"`, and the digest picks each page's largest figure instead of its first -- three fixes to one real failure.** A TI product-change notice's page 5 "Product Attributes" table is rendered entirely as a raster image; `SUMITOMO` appears in it 13 times (`Mount Compound Supplier`, `Mold Compound Supplier`), a text search for it correctly returns zero hits because the word is pixels, and an agent asked "does this document mention SUMITOMO" had no way to learn the table was even worth opening. Three independent bugs stood between the feature and that answer:
  - **The digest showed the wrong figure.** Page 5 also carries a 7.5%-of-page product-label photo *above* the 25.5%-of-page table in document order, and the digest picked whichever captioned entry came first in the `figures` array -- the photo, every time. The table, the one holding the answer, was silently dropped from the one place (the `build_datasheet` manifest) an MCP/Agent-SDK agent actually reads. Fixed in `tools/bound.py:_figure_digest`: each row now carries the page's **largest-area** captioned entry (`page_area_pct`), the same signal that already ranks caption candidates for the `max_figure_captions` cap, so this is a consistent rule rather than a new heuristic. Ties keep whichever entry the scan reaches first in the array's own document order -- never a dict or set's -- so the digest stays byte-stable across runs. On the PCN this changes exactly one row.
  - **A prompt fix alone fabricates.** `CAPTION_SYSTEM_PROMPT` (`llm/figure_captions.py`) now asks for a table's row labels first, then its column headings (a plot's axes and quantity, a diagram's labelled blocks), with an explicit "name only labels you can actually read; if they are illegible, say so rather than guessing" instruction and a "do NOT transcribe cell values, measurements or numbers" bound. Asking for labels the model cannot actually read is not free: with an unchanged prompt but the *previous* `detail: "low"` image (a 512x512 downscale that makes a 20-row, 9-column table illegible), a probe asking the model to list the page-5 table's row headings verbatim, or say it could not, invented `Voltage`, `Wafer Base Supplier`, `Wafer Fab Location`, `Package Fab (OSAT)`, `Package Type`, `Mold Compound Lot Number`, and `Mold Compound Location` -- none of them real rows -- and missed real ones, including both supplier rows. The anti-fabrication instruction does not help when the pixels genuinely are not there to read.
  - **The fix is `detail: "high"`, reversing a documented spec constraint on measured evidence.** `llm/client.py`'s `describe_image` now sends `detail: "high"` instead of `"low"`. The same verbatim-row-headings probe against the same table returned 19 of 20 row headings correct (the one error: `Die Composition` for `Bond Wire Composition`), including both supplier rows and the grey section rows `Die Attributes` and `Package Attributes`. Cost, read from `usage` on live responses rather than estimated: **120 input tokens per image at `"low"`, 1074 at `"high"`** -- about 9x, or roughly 2.4k to 21.5k input tokens per document at the default cap of 20, paid once per document and cached on disk by the existing artifact reuse. A separate token-*counting* endpoint on the validation gateway still returns `405 Method Not Allowed`, which is why an earlier architecture-doc note called the per-image cost unconfirmed; that note is corrected, since `usage` on a real response is a working substitute.
  - Row-labels-first is not stylistic: with column headings named first in the prompt, the table's identifying words (the supplier names) landed at character 442 of the model's reply -- past the digest's caption clip. Moving row labels first moved the same hook (`Mount Compound Supplier`) to character 310.
  - `_MANIFEST_CAPTION_CHARS` (`tools/bound.py`) rises from 200 to 350 so that hook survives the digest's own clip. Measured caption lengths with the final prompt across the PCN's 8 raster regions: median 325 characters, max 601. `_MANIFEST_FIGURE_PAGES` stays 40, so the digest's worst case grows from roughly 8 KB to roughly 14 KB. **Known limit, accepted rather than chased:** `Mold Compound Supplier` sits at character 367 and is still clipped; one surviving supplier hook is judged enough to tell an agent the table holds supplier data, and 350 is the chosen bound, not raised further.

### Removed
- **`locate_text` is no longer an agent tool.** The MCP / Agent-SDK tool surface drops from six tools to five (`build_datasheet`, `get_section_text`, `search_text`, `inspect_page`, `extract_table_markdown`). **`DatasheetTools.locate_text` is unchanged and fully supported** -- this removes only the agent-facing exposure, so library callers, and source-grounding consumers in particular, need no change. Measurement drove it: a hit covers 0.07-0.58% of a page, so following the tool's own advice to feed `region['pct']` into `inspect_page(region=...)` rendered a picture of the query string and nothing more. Seeing the table *under* a matched heading required expanding the region by an amount nothing told the agent, while `inspect_page(page, detail="low")` gives a cheaper overview to crop from what was actually observed. No consumer was found calling the tool -- every real use is Python code calling the method directly, which is what the method is for.

### Fixed
- **`locate_text` now clamps its normalized coordinates to the page.** `pct` is documented as the `inspect_page(region=...)` input, and `inspect_page` *raises* `ValueError: Region 'top' and 'bottom' must be between 0.0 and 1.0` on an out-of-range region -- so a match whose box crossed a page edge made `locate_text` emit a region its own documented consumer rejects. Two ordinary cases produce it: a glyph whose descender crosses the bottom edge, and a CropBox whose origin falls inside the match. The downstream consumer had already hit this in production and carried its own `_clamp01` helper to compensate; that workaround is now redundant, though harmless to keep. **`points` is deliberately left unclamped**, because it means something different -- raw PDF coordinates for annotation and highlighting, where a glyph that really does cross the page edge should be described where it actually sits. The consequence worth knowing: the `pct * page_width == points - page_rect.x0` identity holds for every box inside the page and is intentionally broken for one that overflows.
- **On-disk reuse (introduced in 0.24.0) never actually hit for a document whose extracted text contains a carriage return.** The sidecar records each deliverable's hash with `sha256_file` -- the raw bytes on disk, taken right after the atomic write. The reuse check re-reads the same file with a bare `Path.read_text(encoding="utf-8")` and hashes the resulting string with `sha256_text`. `read_text`'s default universal-newline mode silently rewrites `\r\n` and lone `\r` bytes to `\n` on the way in, so for any document whose text carries a CR the two hashes can never agree again -- every later `build_datasheet` call against that output directory rebuilt from scratch, forever, with `text_hash_mismatch` logged at debug and nothing louder. Found by a live 14-document corpus validation run, where it hit 2 of 14 real datasheets (`microchip-mcp3008.pdf`, `ti-tlv9061.pdf`); their second build dropped from 44-73s to under 20ms once fixed. This fails **closed** -- it always fell back to a correct rebuild rather than serving mismatched bytes -- so it cost time, never correctness. The fix reads with `newline=""` (new `read_artifact_text` helper in `core/artifact_cache.py`, used at both reuse call sites), which disables the translation so `sha256_text(read_artifact_text(path))` is byte-identical to `sha256_file(path)` again; the deliberate hash-*after*-read design from 0.24.0 (closing the mixed-generation window rather than narrowing it, per that entry) is preserved exactly, not routed around. `atomic_write_text` now also writes with `newline=""`, defensively: on Linux/macOS this was already a no-op (`os.linesep` is `"\n"`), but on Windows the previous default would have translated a lone `\n` into `\r\n` on the way out, corrupting content a caller may have already fingerprinted. `pyproject.toml` stays at `0.25.0` for this release; only the fix, its tests, and this entry are new.
- **The VLM figure-captioning pass no longer describes blank regions.** A live 14-document corpus run confirmed a hallucination on `ti-tlv9061.pdf` page 46: a region that is blank white space was captioned as "a schematic diagram ... optocoupler component", and the validator confirmed by rendering the exact region that nothing is visible in it. Root cause is upstream and out of scope for this fix -- that page's mechanical package drawing is exported as 17 overlapping raster XObjects, several of them empty fragments; clustering them into one figure is a larger, deliberately deferred change. The fix instead checks each rendered region with `pymupdf.Pixmap.color_topusage()` right after `inspect_page` renders it, and skips dispatch to the vision client when the region is exactly one distinct colour. That threshold is not tuned, it is measured: across 38 real raster regions from three plot-heavy TI datasheets (tlv9061, opa2134, ads1115) at dpi=150 -- the resolution `inspect_page`'s own `detail="high"` default renders at -- 6 regions measured exactly `1.0` (all confirmed blank fragments on the hallucination page), the nearest real-content region measured `0.9877`, and one near-miss blank fragment measured `0.999743` and is deliberately left uncaught, so a future tightening has real data instead of a guess. A skipped region is neither `failed` nor `pending` on `CaptionOutcome` (new `blank` counter): `failed` propagates to `llm_enrichment_incomplete`, which would rebuild the same document forever for a page that is blank on every build, and `pending` would misreport that no vision client was available when one was simply given nothing captionable to do. `caption` stays `None`, exactly as an uncaptioned entry. The known tradeoff: the guard runs after rendering, so a skipped blank region still consumes one of the caller's `max_figure_captions` slots -- the cap selects candidates before this check runs, and reworking candidate selection is out of scope for this fix.

## [0.24.0] - 2026-07-25

### Added
- **`build_datasheet` now reuses byte-valid artifacts already on disk instead of rebuilding them.** A new sidecar, `<output_dir>/<stem>.build.json`, records the source PDF's sha256 and size, the resolved build options, the exact package version, the sha256 of each deliverable, the complete `TocQuality` (including the `details` string the ToC JSON does not carry), and whether the build's LLM enrichment completed. When all of those match, the two deliverables are read back and returned instead of re-parsing the PDF and re-running the table scan -- measured 7.91s down to 0.01s on a 134-page datasheet. This is the normal path for the library's main consumer: `datasheet-agent` constructs a fresh `DatasheetTools` per comparison request against a stable output directory, so request N's artifacts were already on disk when request N+1 started and were ignored. It benefits with no change on its side. Reuse is default-on; `force_rebuild=True` bypasses it, and deleting the output directory remains safe at all times and is the recovery action for any suspected staleness. The 7.91s-to-0.01s figure is a local-file warm hit; an `http(s)` source is resolved (downloaded to a temp file) before it is fingerprinted, so a warm hit against a URL still pays for the download -- content identity is the only thing that can make a URL cacheable at all, since each download lands on a fresh temp filename with nothing else stable to key on.
- **`DatasheetIndex.artifact_stem()`, `TocNode.from_dict()`, `TocQuality.to_dict()`/`from_dict()`, and a new `datasheetindex.core.artifact_cache` module.** These back the reuse feature above but are public in their own right: `artifact_stem()` derives the same `<stem>` the sidecar and deliverables are named from, so a consumer that wants to locate a document's artifacts without triggering a build can do so directly. `TocNode.from_dict()` and `TocQuality`'s pair are the deserialization side of the existing `to_dict()`s, needed to read a `DatasheetArtifacts` back from disk.

### Fixed
- **The two deliverables are now written atomically** (temp file then `os.replace`) rather than by two bare `write_text` calls. A crashed or failing build previously left a truncated JSON, or a mismatched pair of files if it died between the two writes -- and that pair stayed on disk permanently, with nothing to detect it. It now leaves the previous generation intact. This is also what makes reuse safe to read: a reader validates the sha256 of the bytes it *actually read*, so a pair straddling another process's write, or left mixed by a crash, fails validation and rebuilds rather than being served as a coherent artifact. Hashing after the read rather than stat-ing before it closes that window entirely instead of narrowing it.

### Changed
- **An artifact whose LLM enrichment did not complete is never reused, from disk or from memory.** Two causes set the flag: the ToC fallback was eligible but no client could be created, and the fallback ran and raised. The second is the one that matters -- `index.py` catches every exception from the fallback and continues with the weak native ToC, so before this change a single transient gateway error would have produced an artifact indistinguishable from a successful build, and every fingerprint field would then have matched forever. One dropped connection would have cost that document its ToC for the life of the output directory, with no way to dislodge it short of deleting the directory. A fallback candidate that ran and was *rejected on the merits* deliberately does **not** set the flag: that is a completed decision rather than a failure, and marking it would re-pay the LLM cost on every request for exactly the documents the fallback cannot help. The flag also gates the in-memory cache, so a retry on the same `DatasheetTools` instance rebuilds instead of returning the degraded artifact -- without that the rule would have been unreachable on the MCP path, which holds one instance per document across a whole session. The cost is accepted in one direction: an environment with no credentials configured rebuilds a weak-ToC document on every call rather than serving it from memory, which is the same profile the disk rule already accepts and is the price of not pinning a degraded artifact in place.
- **Reuse is disabled entirely under a directory install** -- editable (`pip install -e .`) or not (`pip install .`) -- detected via the presence of a `dir_info` key in the distribution's `direct_url.json`, and under an uninstalled source tree. `package_version()` returns the real version under both kinds of directory install, so version equality alone would have served pre-edit artifacts after a source change with no version bump -- and `0+unknown == 0+unknown` matches anyway, so exact equality could never have forced a rebuild on its own. Contributors see their edits take effect regardless of which install mode they use. Note the deliberate asymmetry: an index-installed wheel has no `direct_url.json` at all, and a local archive install (`pip install ./dist/foo.whl`) has one without a `dir_info` key -- both *are* reusable, because both are immutable and version equality genuinely suffices there.

### Compatibility at a glance
- **No public signature changed, and both deliverables stay byte-identical** -- the ToC JSON's `toc_quality` block keeps its five keys with no `details`, and cache bookkeeping lives only in the sidecar. Four externally visible differences. A **third file** appears in the output directory, so a consumer that enumerates it should expect `<stem>.build.json` beside the JSON and text file. The deliverables are **replaced rather than updated in place**, so a consumer holding an open handle sees the old content until it reopens. `DatasheetArtifacts` gains two fields, `llm_enrichment_incomplete` (default `False`) and `llm_enrichment_notes` (default `()`), which are additive and need no reader. And a hard kill (`SIGKILL`, power loss) landing between the atomic write's temp-file write and its `os.replace` can leave a `<stem>.<ext>.<pid>.<uuid>.tmp` file behind in the output directory, which nothing reclaims -- a Python-level failure always cleans up after itself, so this is the hard-kill case only. `build_batch` and the CLI still call `build()` directly and therefore always build, writing no sidecar -- both pass an explicit `output_dir` and exist to produce artifacts. The output directory is now a cache rather than scratch space.

## [0.23.0] - 2026-07-25

### Fixed
- **One bad page number from the LLM ToC fallback no longer corrupts the section around it.** `toc_fallback.py`'s prompts asked the model to return only pages supported by the chunk it was given, and nothing checked the answer: `_normalize_entries` enforced `start_page >= 1` and `validate_toc_entry` the same, with no upper bound anywhere. The damage was not local to the bad entry. `compute_end_pages` derives each node's `end_page` from its *next sibling's* `start_page`, so on a 12-page document a hallucinated page 9999 produced `Real: 1-9998` alongside `Bogus: 9999-9999` — the preceding section silently swallowed the whole document, and every consumer of that range (`extract_section_text`, `_apply_table_counts`, breadcrumbs) inherited it. Entries whose `start_page` is absent from the `--- PAGE N ---` markers of the chunk that produced them are now dropped, per chunk, with the rejected titles and pages named in a warning. **Dropped, not clamped:** a plausible-looking wrong page is worse than a missing section, and a candidate thinned by drops is still weighed by `_accept_llm_toc_candidate()`, which keeps the original ToC if the result came back too thin — so every failure direction lands on keeping the safe thing. Against the fallback's most common trigger (a PDF with no bookmarks at all) the min-entries floor is skipped, so a couple of drops do not cost the ToC.
- **A marker-shaped string inside a page body can no longer forge an attested page.** Validating against the chunk's markers is not sufficient on its own, because the markers are not independent of the document: `generate_text` appends extracted page text **verbatim**, so a datasheet whose page-3 body prints `--- PAGE 9999 ---` injects a marker that `_page_markers` then accepts. That reproduced the exact corruption above on a 3-page document, reached through the untrusted-input vector the library already documents (the CLI accepts arbitrary `http(s)` URLs). Entries are now checked against the marker set **and** the real page count: the markers catch a plausible-but-wrong page, the page count catches an impossible one no matter who wrote the marker. This also bounds the page range downstream — `assess_toc_quality` and `_apply_table_counts` both walk `range(start_page, end_page + 1)`, so a forged nine-digit page previously built a set that size.
- **A chunk beginning mid-page now carries that page's marker.** `_split_into_chunks` splits between a marker and its body, so a chunk could open on orphan text with no page for the model to cite — measured on a real 134-page datasheet, **13 of 15 chunks** did exactly that. Harmless before (the model simply had no anchor for those pages); under the validation above it would have discarded every section starting on those 13 boundary pages. The current marker is now repeated at the head of such a chunk. It repeats only a page already seen, never invents one: text preceding the first marker stays unanchored, because attributing it to a page it did not come from would make the model cite a page the text never occupied.

### Changed
- **Document text sent to an LLM is now framed as data.** PDF text reached both LLM prompts by direct interpolation, and datasheet text is untrusted by construction — the CLI accepts arbitrary URLs, and whatever a PDF carries arrives verbatim. New `llm/untrusted.py` wraps it in `<document_text>` tags and adds a `DATA_ONLY_INSTRUCTION` to the system prompts of both `toc_fallback.py` and `summarizer.py`. Any `<` that would open or close that tag — in any spacing or casing — is escaped, so text cannot break out of its own frame and have what follows read as prompt. The summarizer is the sharper path: its output lands in `node.summary` in the emitted ToC JSON, which a consuming agent reads as *trusted* context, so an instruction printed in a datasheet section would otherwise propagate straight through. Framing is not a claim of safety; it gives the model an unambiguous boundary, which is the part we control. Deliberately **not** done: redacting injection-looking keywords from document text, as PageIndex does. It is trivially bypassable, and "act as", "do not follow" and similar are ordinary English in application notes — it would corrupt real content in exchange for no real defence.
- **All four chunk prompts now state the rule that is enforced.** Validation runs on both extraction paths, but only `STRUCTURED_INIT_USER_PROMPT` told the model about it. The free-text prompts are used when the gateway cannot do structured output — the weaker-model case, which needs telling most — and were being penalized for a rule they were never given.

### Compatibility at a glance
- **No public signature changed**, and a document with a usable embedded ToC is bit-for-bit unaffected: verified byte-identical against 0.22.0 on a 134-page datasheet, both with and without LLM credentials available, since a ToC scoring above `TOC_FALLBACK_THRESHOLD` never reaches this code. The externally visible differences are confined to the LLM paths. **The prompt text changed** on both of them, which is worth checking only if you inject an `LlmCallable` that matches on prompt content rather than treating it as opaque — the `(system, user) -> str` contract is unchanged and the document text now arrives inside `<document_text>` tags. A fallback-generated ToC may now contain **fewer** entries than 0.22.0 would have produced, which is the point: the omitted entries cited pages their chunk could not support. Summary *wording* may shift slightly, since the summarizer's system prompt gained the data-only instruction.

## [0.22.0] - 2026-07-25

### Fixed
- **`inspect_page` no longer fails on every call through `create_datasheet_tools_server()`.** The neutral envelope spelled the image media type `mime_type`, but `claude-agent-sdk`'s `create_sdk_mcp_server` converter reads `item["mimeType"]`, so the SDK surface raised `KeyError('mimeType')` for every `inspect_page` call — from at least 0.17 through 0.21.0. The agent-visible symptom was uniquely unhelpful: the `KeyError` escapes *after* our handler has already returned successfully, so it is not caught by the handler's own `except`; it propagates into the MCP low-level server, which stringifies it with a bare `str(e)`. The entire tool result text was therefore `'mimeType'` — no exception type, no tool name, no traceback — which reads like truncated output rather than an error, and went untraced in a downstream deployment for roughly two months. The envelope now emits **both** `mime_type` and `mimeType` with the same value. Both are required and neither is transitional: the envelope is the SDK's format, and that format is mixed-case by construction — the SDK reads `is_error` (snake_case) and `item["mimeType"]` (camelCase) from the same dict — so renaming to match "MCP naming" would break `mcp_server._envelope_to_content` and every host already reading the documented snake_case key. The packaged stdio MCP server (`datasheetindex mcp`) was never affected; it translated the key correctly on the way out. Reported and diagnosed in #13.
- **Error envelopes now name the exception type.** Every handler wraps its body in a blanket `except Exception` and reported `str(exc)`, which is the worst case for exactly the exceptions such a guard catches most: `KeyError` and friends stringify to their bare argument, so a host omitting a required argument got a tool result whose entire text was `'end_page'`. Handler-raised exceptions are now reported as `"TypeName: message"` (`"KeyError: 'end_page'"`, `"ValueError: Page 9999 out of range..."`). Messages a handler writes itself are unchanged — `"pdf_source is required"` does not become `"str: pdf_source is required"`. Note this is an independent diagnosability fix and **would not** have made the `'mimeType'` failure above legible, since that exception never passed through `_err`; the two fixes address different layers, and only the first one closes #13.

### Added
- **An optional `sdk` dependency group, and tests that run the real SDK.** `create_datasheet_tools_server` is only as correct as the converter it feeds, and the suite stubbed that converter out entirely: the fake `create_sdk_mcp_server` accepted the envelope and never read a key from it, so the envelope was free to spell a key any way it liked and every SDK test still passed. That blind spot is why #13 shipped. Coverage is now two-layered. `tests/conftest.py:sdk_envelope_to_content` mirrors the real converter key for key and runs in the **default** lane, so a key-name regression fails a plain `uv sync && pytest`. `tests/test_sdk_integration.py` drives the genuine `claude-agent-sdk` through its real `CallToolRequest` handler and pins the mirror against it, so the mirror cannot silently go stale if upstream renames a field. It needs `uv sync --group sdk` and skips without it — deliberately not in `dev`, because the wheel unpacks to ~263 MB of which ~262 MB is a bundled `claude` CLI binary these tests never invoke, five times the layout extra that is already kept out of the default sync for the same reason.

### Compatibility at a glance
- **No public signature changed, and the image block is a strict superset of what it was** — `mime_type` is still present with the same value, so a host reading it needs no change. The externally visible differences are the added `mimeType` key, and the `"TypeName: "` prefix on error text for handler-raised exceptions. The latter is worth checking if you match tool-error strings exactly rather than by substring; messages the handlers author themselves are unaffected. Note that through a schema-validating host (the SDK and stdio MCP surfaces both validate), a *missing required argument* is rejected before dispatch and never reaches a handler, so its message comes from the MCP server, not from us — the prefix applies to exceptions raised inside a handler.

## [0.21.0] - 2026-07-21

### Fixed
- **`build_datasheet` no longer hangs forever on Windows.** Any document at or above the 12-page parallel threshold hung indefinitely when the library ran as an MCP stdio server on Windows; below it, the sequential path returned normally in ~4s. The cause is that a `ProcessPoolExecutor` created *inside* an MCP stdio server deadlocks on Windows: the workers are created but freeze before their interpreter finishes initialising, and only unblock when the server process exits, so `shutdown(wait=True)` never returns. This is upstream's bug (modelcontextprotocol/python-sdk#817, open) and is not fixable from inside the worker -- `_subprocess_init` runs as the pool *initializer*, long after the child is already stuck. The trigger is the combination, not any one ingredient: measured on Windows, `spawn` alone (5.9s), an open stdin pipe (5.9s), `asyncio.to_thread` under a ProactorEventLoop (5.7s) and a full `build_datasheet` in a plain process (6.4s) all complete normally. On win32 the scan is now delegated to a single child process (new `core/_scan_worker.py`) launched with `stdin`/`stdout` on devnull, which severs it from the server's JSON-RPC handles; a plain process pools normally, so **parallelism is preserved rather than traded away** -- 31.4s on a 148-page datasheet that previously never returned. Threads were evaluated as the alternative and rejected on measurement: 0.88x (slower than sequential) *and* wrong counts, because PyMuPDF is not thread-safe for concurrent `find_tables()`. Non-Windows platforms keep the in-process pool unchanged; a same-process A/B measured 18.5s before and 18.3s after.
- **A stalled parallel scan now degrades to a sequential one instead of blocking.** `enrich_with_table_counts` has always recovered from a failed pool by falling back to sequential, but that guard could never fire: `_build_table_count_cache_parallel` ran `pool.map` -- which returns a *lazy* iterator -- inside a `with` block and materialised it outside, so `__exit__` reached `shutdown(wait=True)` before a single result had been read, and a wedged pool blocked rather than raised. The pool is no longer created under `with` at all: the map is materialised while the executor is still live, bounded by `_scan_timeout()` (one second per page, floored at 120 and capped at 600 so the fallback is still reachable inside the caller's own request timeout), and any failure goes through `_abandon_pool()`, which prefers `kill_workers()` (Python 3.14+) over `shutdown(wait=False, cancel_futures=True)`. That distinction matters: `shutdown(wait=False)` returns promptly but leaves the executor's manager thread joining its workers, and `concurrent.futures` joins that thread from an `atexit` hook, so on 3.13 a wedged worker still hangs the process at exit rather than during the call. The delegating Windows path is bounded the same way, with a grace margin over the child's own deadline so the child fails first and its traceback is reported rather than raced to a kill; its stderr goes to a file rather than a pipe, because the child's own pool workers inherit fd 2 and a pipe would make the parent wait for an EOF that killing the child cannot deliver. A result covering fewer pages than the document is rejected, since `_apply_table_counts` treats a missing page as zero tables and would otherwise ship a confident wrong answer. `DATASHEETINDEX_PARALLEL=0` (also `false`/`no`/`off`) forces the sequential scan for hosts where process creation misbehaves.
- **A path from the other side of a WSL/Windows split now resolves, in both directions.** With VS Code opened on a WSL folder from Windows, the editor, the agent and the files live in the distro, but a gallery-installed MCP server runs on the Windows host -- where `/home/you/ds.pdf` does not exist. PyMuPDF's `no such file` was accurate and useless: the agent cannot detect the namespace split, so it retries the same path and concludes the tool cannot read local files. `index._resolve_local_path` bridges it whichever way the split falls. On a Windows host it maps `/mnt/<drive>/...` back to `<DRIVE>:\...` (WSL's own mount, so the mapping is exact, and it is tried first -- and because the candidates are generated lazily, a path that resolves there never queries WSL at all, which matters because probing a UNC path against a *stopped* distro starts it) and anything else to `\\wsl.localhost\<distro>\...`, which Windows and PyMuPDF both open directly. On a POSIX host it does the mirror: `C:\Users\you\ds.pdf` becomes `/mnt/c/Users/you/ds.pdf`, and a `\\wsl.localhost\<distro>\...` UNC path unwraps to the plain POSIX path it already is. That direction is not hypothetical -- running the server inside WSL is the recommended setup, and a path copied out of Windows Explorer is the natural thing for a user to paste. Translation is consulted **only** when the literal path fails to resolve, so a path that is already correct for the host is never rewritten, and when no candidate exists the original is returned unchanged so the error names what the caller actually passed rather than a rewrite they never mentioned. Verified end to end against real servers on both hosts, for every path form. Scope is the input PDF only: `output_dir` is not translated, because a directory that does not exist yet cannot be probed and the returned artifact paths would still be in the server's namespace.

### Compatibility at a glance
- **No public signature changed**, and no behaviour changes on Linux or macOS: the parallel scan there is the same in-process pool, producing identical per-page counts (asserted against the sequential path and against the delegated path). The externally visible differences are all on Windows -- calls that used to hang now return, and a POSIX path that used to fail may now resolve -- plus the new `DATASHEETINDEX_PARALLEL` escape hatch.

## [0.19.0] - 2026-07-13

### Added
- **The LLM ToC fallback now uses structured output where the gateway supports it, and fails loudly instead of silently truncating.** Previously `generate_toc_from_text` sent a free-text prompt and best-effort-parsed whatever JSON it could find in the reply; a truncated or malformed chunk response just meant fewer entries, with nothing to distinguish that from the document genuinely having fewer sections. `llm/client.py` now exposes an optional `StructuredLlmCallable` protocol (`structured_json(system, user, *, name, schema, max_output_tokens=None) -> StructuredLlmResult`) alongside the existing free-text `LlmCallable`, detected via `get_structured_output_client()` without changing the base protocol callers already depend on. When the LLM client backing `build()` supports it, `toc_fallback.py` calls `responses.create(..., text={"format": {"type": "json_schema", ...}, "strict": True})` per chunk against a fixed `entries: [{level, title, start_page}]` schema; a chunk response that reports `status` as something other than `"completed"`, or whose payload is malformed, is logged and skipped rather than silently contributing zero entries. Skipped means skipped, not fatal: the entries already collected from the *other* chunks still form the candidate, and whether that candidate is too thin to trust is decided by `_accept_llm_toc_candidate()` (below), not by the parse loop — one truncated chunk of forty must not discard the other thirty-nine. A `status` the gateway never reports (`None`) is not truncation and is accepted; only an explicitly non-completed status is. If the structured path yields no entries at all — a model or gateway that rejects `text.format=json_schema` outright — the whole document is retried with the free-text prompt, so an unsupported model degrades to 0.18.0's behavior instead of losing the ToC entirely. Callables that don't expose `structured_json` keep using the original free-text prompt and parsing path — this is additive, not a breaking change to `LlmCallable`. Verified against the internal LiteLLM gateway with both `gpt-4.1` (the unchanged repo-wide default) and `gpt-5.4-mini`.
- **A regenerated ToC can no longer replace a working one just because it scores well on paper.** `assess_toc_quality`'s page-coverage term treats a lone node whose `end_page` was extended to the document's last page (a `build_tree()` side effect on any node without a following sibling) as if it covered the whole document, so a nearly empty LLM fallback result could score deceptively close to, or above, the original. `index.py`'s fallback step now builds the LLM result into a `candidate_nodes`/`candidate_quality` pair without touching `nodes`/`toc_quality` yet, and only accepts it via a new `_accept_llm_toc_candidate()`, which rejects a candidate that (a) has no entries, (b) doesn't score strictly better than the baseline, (c) has fewer entries than `_minimum_fallback_candidate_entries(total_pages)` (1 for very short documents, up to 3 otherwise), or (d) loses more than 5 points of page coverage relative to the baseline. Gate (c) applies only when there is a real ToC to protect: the fallback's most common trigger is a PDF with no bookmarks at all, and against an empty baseline a thin ToC still beats no ToC — a page-scaled floor there would ship `"toc": []` for short datasheets that 0.18.0 indexed fine. There is deliberately no "candidate lost too many entries versus the baseline" gate: the score already weights entry count, coverage, and depth, so vetoing a strictly higher-scoring candidate for being smaller than a bloated junk baseline would keep the junk. Both the acceptance and rejection paths are logged with the specific reason.
- **Continuation prompts for multi-chunk documents no longer duplicate entries or grow prompt context unboundedly.** `toc_fallback.py` previously appended every chunk's raw entries to the running list and re-sent the entire accumulated ToC as context for the next chunk. New `_dedupe_entries()` drops entries that repeat an already-seen `(level, title, start_page)` triple across chunk continuations, and new `_format_previous_entries()` caps the "previous entries" context sent back to the LLM at 4000 characters / 50 entries, trimming the oldest entries first — addressing the same class of unbounded-context growth that motivated PageIndex's own recent hardening of its chat-history handling.

### Compatibility at a glance
- **Purely additive.** No public signature changed: `llm_callable` still accepts a plain `(system, user) -> str` callable, `build()`'s parameters and return type are unchanged, and the fallback continues to activate only when the ToC quality score is below `TOC_FALLBACK_THRESHOLD` and an LLM callable is available. The only externally visible difference is that a poor fallback result is now more likely to be rejected in favor of the original (possibly also poor) ToC, and a broken structured chunk now surfaces as a logged, skipped chunk instead of silently thinning the ToC.

## [0.18.0] - 2026-07-13

### Added
- **`get_section_text` now warns when the requested range cuts content the publisher marked as continuing onto an adjacent page.** An agent that reads a whole ToC section can still silently lose rows, because the section's page range does not always contain the whole of its content, and the evidence of the cut -- the publisher's `(continued)` marker -- sits at the top of the page the agent did not fetch. Measured on the TI TCAN1044A-Q1: section `6.4 Recommended Operating Conditions` has ToC range pages 4-4, but its table continues onto page 5, so `get_section_text(4, 4)` -- exactly what the tool description tells an agent to do for a whole-section read -- silently drops `TJ` (operating junction temperature) and the "without VIO" `IOH(RXD)`/`IOL(RXD)` current variants. Worse, page 4 *does* carry the "with VIO" values, so an agent asking for RXD output current finds a plausible number and never learns the other variant exists. `get_section_text` now probes both boundaries of the *requested range* (new `core.structure.continuation_at_boundary`, backed by a new positional matcher `_CONTINUATION_RE`/`_OPENING_BLOCK_LINES`) and inserts a `=== NOTE: ... ===` line under the position header when either edge cuts marked content. The `===` wrapping marks the line as tool framing, not document content -- real datasheets (e.g. TI TCAN1044A-Q1 page 26) contain their own literal `NOTE:` lines in body text, and a bare `NOTE:` prefix would collide with them. The check is deliberately range-relative, not section-relative: the TI case is a whole-section read, so a section-aware check would miss it entirely. This is a separate concept from `TocNode.continued_tables` (tables captioned `Table N ... (Continued)`), which is unchanged.
- **Silence is not a completeness claim.** The note states only that the publisher marked the adjacent page as continuing -- never that rows or column headers are missing, and never that the range is complete (in the TI case the continuation page in fact repeats its `MIN NOM MAX UNIT` headers, so a stronger claim would be false for the very document that motivated this). The absence of a `=== NOTE: ... ===` line means no continuation was detected, not that the fetched context is whole: content can still spill across a page break with no marker at all, or share a line with trailing text that the marker's `$` anchor does not match -- both are accepted, documented limitations, not bugs.

### Compatibility at a glance
- **Output change, backward compatible.** `get_section_text`'s return value can now include one or more `=== NOTE: ... ===` lines between the position header and the section text. No method signature changed; existing callers that pattern-match only on the header and the `--- PAGE N ---` markers are unaffected.

## [0.17.3] - 2026-07-10

### Fixed
- **`table_count` no longer depends on the indexing process's import history.** `enrich_with_table_counts` has two scan paths, and they disagreed. The parallel path runs `find_tables()` in fresh worker processes that never import `pymupdf4llm`, so it always used PyMuPDF's classic geometric detector. The sequential fallback runs in the caller's process, where importing `pymupdf4llm` -- as `mcp_server._preload_layout_model()` does at startup, and as any earlier `extract_table_markdown` call does -- installs an ONNX-backed hook at `pymupdf._get_layout` that `find_tables()` consults on every call. Both paths now scan inside a `classic_tables()` guard, so counts come from the classic detector always. They are a stable property of the document; the ML engine remains available to `extract_table_markdown`, which is what it was for. Fixes #12.
- **A concurrent `extract_table_markdown` can no longer be broken by an index build.** The `pymupdf4llm` import is what installs the layout hook, and `build_datasheet` and `extract_table_markdown` both run under `asyncio.to_thread`. An import racing the new guard would let it restore a stale `None` over the freshly installed hook; because `pymupdf4llm._use_layout` stays `True`, `to_markdown()` would then route into `_layout_to_markdown`, iterate a `None` `page.layout_information`, and raise `TypeError` -- permanently, since the module is cached. A new `core/engine.py` owns both the hook and the import, serializing them on one re-entrant lock. It is now the only module under `src/` that imports `pymupdf4llm`.

### Changed
- **The 0.17.2 note below overstates the mechanism.** Importing `pymupdf4llm` does not replace `find_tables()`; the function is never rebound. It sets the module-global `pymupdf._get_layout`, which `find_tables()` consults per call. The distinction is what makes the fix above possible: the engine is selectable per call, and saving and restoring that global costs ~20us. The "one to two orders of magnitude" slowdown holds for ruled-grid and unruled synthetic fixtures; on a real 68-page datasheet the layout engine is ~4.4x slower, and finds *fewer* tables (39 vs 75), because the classic detector false-positives on plot gridlines.

## [0.17.1] - 2026-07-09

### Fixed
- **Parallel table counting no longer forks the caller, and sizes its pool from the cgroup CPU quota.** `_build_table_count_cache_parallel` derived `max_workers` from `os.cpu_count()`, which reports the *host's* cores and is blind to the cgroup CPU quota, so a 42-page PDF in a 1-CPU container on a 128-core node spawned 42 workers. Combined with the `fork` start method (multiprocessing's default on Python <= 3.13) this caused two production failures in long-running services: container OOM kills (each copy-on-write child costs ~26 MiB of the parent's heap), and a permanently wedged pod -- a child forked while another thread held an allocator lock deadlocked on a mutex it could never see released, and because it also inherited every open file descriptor it held the parent's `flock`-based admission lock open forever, while `pool.map` blocked on it indefinitely. Two independent changes fix this:
  - Workers are now `min(available_cpus, total_pages, 8)`. `_available_cpus()` reads the cgroup CPU bandwidth quota (v2 `cpu.max`, v1 `cpu.cfs_quota_us`) and takes the tighter of that and `os.process_cpu_count()`; note that `sched_getaffinity` cannot see a CFS quota, since it is not an affinity mask. The quota is resolved against the process's *own* cgroup via `/proc/self/cgroup`, with the tightest quota along the ancestor chain winning -- reading the hierarchy root alone would miss a quota applied to a nested cgroup, as systemd's `CPUQuota=` does on a bare host. The hard ceiling of 8 also bounds memory on an unconstrained host, where page-level `find_tables()` does not scale past a handful of processes anyway.
  - The pool now runs under `forkserver` (falling back to `spawn` where forkserver is unavailable, i.e. Windows) instead of `fork`. Children are no longer forked from the caller, so they inherit neither its open file descriptors nor its held mutexes -- this is what actually eliminates the deadlock. A library cannot know whether its caller is multithreaded, so it must not fork one. Behaviour is now identical on Python 3.13 and 3.14 (which changed its own default to `forkserver`). Closes #9.

  **Compatibility.** The parallel path now obeys multiprocessing's "safe importing of main module" rule on Linux, as it already did on Windows and macOS. **Guard your entry point with `if __name__ == "__main__":`.** A caller whose `__main__` script runs `build_datasheet()` at module scope without that guard has its entire top-level body re-executed once, in the forkserver process (once, not once per worker). Results stay correct, but the consequences differ by caller: if the re-executed body completes, the calling process keeps its parallelism; if it raises -- which a non-re-entrant entry point typically will -- the forkserver dies, and the caller falls back to a sequential scan (now logged at `warning`, previously silent at `debug`). Code that drives the parallel builder directly, outside `enrich_with_table_counts` and its fallback, will fail outright. Callers using the `datasheetindex` CLI, `python -m`, or any guarded entry point are unaffected.

  **Throughput is now bounded rather than unbounded.** On ~200 ms/page documents the pool delivers ~3.7x over sequential at 40 pages and ~1.4x at the 12-page parallelism threshold. On a host with more than 8 free CPUs the scan is slower than before, by design: the old code used up to one `fork` per page with near-zero startup, and the new one caps at 8 `forkserver` workers that each pay real startup cost. That ceiling is the point -- it is what bounds memory and prevents the fan-out this release fixes.

### Changed
- **`_ResponsesOutput.output_text` is now declared as a read-only property** rather than a mutable attribute. The pipeline only ever reads it, and openai's `Response.output_text` is a `@property`, which cannot satisfy a mutable protocol attribute -- a latent declaration error that the upgraded `ty` correctly rejects.

- Refreshed the lock to the latest compatible versions (`uv lock --upgrade`, all extras synced): `cffi` 2.0.0 -> 2.1.0, `filelock` 3.29.5 -> 3.29.7, `numpy` 2.5.0 -> 2.5.1, `python-discovery` 1.4.2 -> 1.4.4, `tqdm` 4.68.3 -> 4.68.4, `ty` 0.0.56 -> 0.0.57, `uvicorn` 0.49.0 -> 0.51.0, `virtualenv` 21.5.1 -> 21.6.0. ## [0.13.0] - 2026-05-15

### Added
- **`breadcrumb` field on every ToC node.** Pre-computed full ancestry path joined by `" > "` (e.g. `"5 Electrical Characteristics > 5.1 Absolute Maximum Ratings > 5.1.1 Junction Temperature"`). Computed in `assign_breadcrumbs()` and wired into `build_tree()`, so every code path -- including the LLM ToC fallback -- gets breadcrumbs without extra calls. Verified at 100% coverage on Infineon (66/66 nodes), TI (45/45), and NXP (108/108) live datasheets. Omitted from JSON when empty (e.g. legacy code constructing bare `TocNode` instances).
- **`boilerplate_category` field on ToC nodes.** New `core/boilerplate.py` module classifies titles into one of six categories -- `legal`, `ordering`, `revision`, `contact`, `toc`, `glossary` -- via title-only regex matching (no LLM, no text scanning). Title normalization strips leading section numbering (`12.3.4`, `Appendix A:`, `Chapter 3 `) and trailing punctuation before pattern matching, so `"12 Revision History"`, `"Appendix A: Ordering Information"`, and `"REVISION HISTORY"` all classify correctly. Substantive sections that merely mention boilerplate keywords (e.g. `"Trademark Licensing Strategy"`, `"Order of Operations"`, `"Glossary of Register Names"`) intentionally do not match. Bare ambiguous words (`"Information"`, `"Notice"`, `"Liability"`) require an explicit qualifier (`legal`, `important`, `product`) to match, since the bare forms are common substantive titles. Classification rule: a node's own classification wins; a node with no own classification inherits its parent's category (so an unlabelled "Rev 1.2 changes" subsection under "Revision History" inherits `revision`, but a substantive "Electrical Characteristics" subsection nested under a misclassified parent keeps its empty classification). English-only by design. Empty when no match -- omitted from JSON in that case.

- **`DatasheetTools` internals** - Now delegates to `DatasheetIndex` rather than
  managing its own `pymupdf.Document`, inheriting URL support and temp file handling.
- **`toc_fallback.py`** - Eliminated duplicated tree builder; now calls `build_tree()`
  from `structure.py` directly.
- **Public API naming** - Renamed `_validate_toc_entry`, `_compute_end_pages`, and
  `_assign_node_ids` to drop the underscore prefix since they are used across modules.
- **Exception handling** - `_try_create_default_llm_client` now catches only
  `(ImportError, ValueError, OSError)` instead of bare `Exception`.
- **Filename sanitization** - Output filenames are truncated to 200 characters to stay
  within OS path length limits.
